# Testing and Comments

Playbook for deciding what to test, how to write tests, and what comments and
docstrings to write. Hard constraints live in the global AGENTS.md
(Testing & Comments section); this file provides the reasoning, the
taxonomy, and the examples.

This skill does not define general production-code review. Use
`bounded-code-review` for requirements, maintainability, or verification review;
use this skill only for the tests, comments, and docstrings within that work.

## 1. What to test

Decision rule: does the code make decisions? Branches, calculations,
validation, parsing, state transitions, and error handling imply decisions,
so test them. Pure data movement does not.

### Test

- Branches, math, validation, parsing/formatting, conversions.
- State management: caches, retry logic, sessions, lifecycles.
- Public contracts: public APIs and anything other modules depend on.
- Untrusted input handling: user input, network data, files; test both the
  validation and the error paths.
- Bug fixes: add a regression test that fails before the fix and passes
  after. A fix without a regression test is not a fix.

### Do not test

- Plain data definitions: fields, constants, enums without logic
  (POJO/DTO/record/struct).
- Trivial getters/setters, one-line delegation, direct assignment.
- Framework-guaranteed behavior: dependency injection, routing, rendering,
  ORM SQL generation, CLI parsing libraries.
- Generated code: protobuf output, scaffolds, build artifacts.
- Throwaway scripts, unless the user states the script is meant to live on.

### Anti-patterns (tests that are net-negative)

- Testing private implementation details or internal call order: every
  refactor turns the suite red, and the tests become a paraphrase of the
  implementation.
- Over-mocking: stubbing every dependency so the test asserts mock
  orchestration instead of behavior. Prefer real implementations or simple
  fakes; mock only at the boundaries (network, filesystem, clock, database).
- Adding tests only to raise line coverage: coverage is a guardrail, not a
  goal. Target about 80% on critical modules and full behavior coverage on
  tricky logic, not 100% line coverage.
- Re-verifying what the framework already guarantees.

## 2. Test characteristics

- Fast: unit tests run in milliseconds; slow suites get skipped.
- Deterministic: no sleeps, no wall-clock or locale dependence, no live
  network; use fixed seeds and fake clocks. A flaky test is worse than no
  test, because it destroys trust in the suite.
- Independent: no shared state, no order dependence; each test creates and
  cleans up its own state.
- Focused: one behavior per test; Arrange-Act-Assert (Given-When-Then).
- Readable: name describes behavior, not implementation:
  `test_calculates_discount_for_vip_customer`, not `test_foo_2`. Prefer
  `<verb>_<subject>_<condition>_<expected>`.

## 3. Structure and scope

- Cover edge cases: empty input, boundaries (0, max, min), invalid input,
  repeated calls, concurrent access.
- Test through public interfaces; internal helpers are covered indirectly.
- For a bug fix, write the regression test first (or verify it fails on the
  old code), then fix.
- Keep the suite green in CI; never skip or disable a test to "unblock" a
  change.

## 4. Comments and docstrings

Core rule: comments explain why, not what. If a comment restates the code,
delete it. If code needs a comment to explain what it is, rename or
refactor instead.

### Deserves a comment

- Rationale: why this implementation, what trade-offs were made.
- Business rules and domain constraints: tax logic, timezone handling,
  legacy data quirks.
- Warnings and gotchas: not thread-safe, has side effects, must be called in
  pairs.
- References: spec links, issues, RFCs (evidence of why something exists).
- TODO/FIXME markers: always carry an owner and an issue link.

### Never write

- Restating the code (`i++ // increment i`).
- Line-by-line narration of what the code does.
- History logs; git blame and git log exist for that.
- Commented-out code: delete it, git history preserves it.
- Authorship, dates, or "generated by AI" markers.

### Docstrings: public vs private

Public APIs and exported symbols: contract docstring is required:

- Purpose in one sentence, imperative mood: "Add two numbers", not "This
  function adds two numbers".
- Parameters: meaning, units, optional or required, allowed ranges.
- Return value and its meaning; spell out what `None` means.
- Raised errors: when and which ones.
- Side effects: mutation, resource consumption, cache invalidation.
- A usage example when the behavior is non-obvious.

Private functions: no docstring by default. Write one only when the name and
signature cannot convey the intent:

- Non-obvious choice ("binary search because input is sorted").
- Hidden preconditions ("must hold the lock before calling").
- Surprising side effects ("empties the internal cache").
- Easy-to-misread output conventions ("None means cache miss").
- Algorithmic complexity: bit tricks, state machines, grammar rules.

Why not every function: signal-to-noise. Comment density should be
proportional to non-obviousness. Every docstring is a liability that can go
stale, and a stale comment is worse than no comment. Google style guides do
not require comments on private functions; golint only checks exported
symbols; PEP 257 targets accessible interfaces.

## 5. Per-language notes

- Python: docstrings in Google, Numpy, or Sphinx style, matching the
  project; doctest examples for pure functions; pytest/unittest with
  `test_*.py`; parametrize for input tables; Hypothesis for property-based
  tests on complex invariants.
- TypeScript/JavaScript: JSDoc `@param`/`@returns`/`@throws` on exported
  APIs; vitest/jest `*.test.ts` with `describe`/`it`; snapshot tests for
  renderers and serializers (review snapshots carefully).
- Rust: rustdoc on public items; doctests; one `#[test]` module per file;
  proptest for property-based tests.
- Go: golint requires comments on exported symbols; table-driven tests with
  subtests are idiomatic.

## 6. When to ask the user

- Introducing a new test framework or CI pipeline into a project that has
  none.
- Deciding how much integration/E2E infrastructure to add (compose files,
  staged environments).
- Coverage thresholds: whether to enforce a hard percentage gate in CI.
